# Bridging the Gap: Two Weeks of Integration Surgery

*How connecting a SwiftUI app to its Cloudflare Workers backend became an exercise in careful refactoring*

---

In the last post, I described the integration gap—two complete systems that didn't talk to each other. An iOS app full of fake data. A backend with 65 endpoints that nobody called. The estimate was seven to ten days of work.

It took closer to two weeks. Here's what actually happened.

## The Foundation: Building the Networking Layer

The first real work was infrastructure nobody would ever see. Before any feature could talk to the backend, I needed the plumbing to make HTTP requests happen.

`APIClient` became the heart of the networking layer. It's an actor (Swift's way of making concurrent code safe) that handles everything HTTP-related:

```swift
actor APIClient {
    static let shared = APIClient()
    
    private var accessToken: String?
    private var refreshToken: String?
    private var isRefreshing = false
    private var refreshWaiters: [CheckedContinuation<Bool, Never>] = []
    
    // ... 500+ lines of request handling
}
```

A few decisions shaped the implementation:

**Snake case conversion happens automatically.** The backend uses `snake_case` (TypeScript convention), the app uses `camelCase` (Swift convention). Rather than manually mapping every field, the JSON decoder handles it: `decoder.keyDecodingStrategy = .convertFromSnakeCase`. One line of code, zero field mapping errors.

**Token refresh is coordinated.** When an access token expires, multiple requests might fail simultaneously. Naively, each would try to refresh the token, causing race conditions. The solution: when a refresh is in progress, other requests wait in a queue. When the refresh completes, all waiters resume together.

**Errors are typed, not stringly.** Rather than passing error messages as strings, I created an `APIClientError` enum with specific cases: `unauthorized`, `networkError`, `apiError`, `decodingError`. Each service can then convert these into user-friendly messages appropriate for its context.

The networking layer is 544 lines of code. It's not glamorous work, but it's the foundation everything else relies on.

## Authentication: Making Users Real

With networking in place, authentication came next. The `AuthService` manages the entire auth lifecycle:

```swift
@Observable
@MainActor
class AuthService {
    enum AuthState {
        case unknown
        case unauthenticated  
        case authenticated(APIUser)
    }
    
    private(set) var state: AuthState = .unknown
}
```

The state machine is simple but important. When the app launches, the state is `unknown`—we don't know yet if there's a valid session. The `RootView` shows a loading indicator. Then `restoreSession()` runs, checks the Keychain for tokens, validates them against the backend, and transitions to either `authenticated` or `unauthenticated`.

Sign in with Apple was straightforward once I understood the flow. Apple gives you a cryptographic token proving the user owns a certain Apple ID. The backend verifies this token, creates (or finds) a user, and returns JWT tokens for future requests.

The tricky part was handling the name. Apple only sends the user's name on the first sign-in. If you don't capture it then, it's gone forever. The solution is to check for the full name, construct a display name from the parts, and send it to the backend along with the identity token.

## The Migration: From Mock to Real

Here's where the real work began. Every view in the app was calling `MockDataService.shared`. Every view needed to call real services instead.

I started with a migration pattern that worked well:

1. **Create the service** with the same interface shape as the mock
2. **Update the view** to use the new service
3. **Test the happy path** with real data
4. **Add error handling** that was never needed with mocks
5. **Move to the next view**

Some migrations were simple. The `BadgesView` needed to fetch badges from the API instead of a hardcoded array. Swap one service for another, add a loading state, done.

Others were complex. `GroupsView` turned out to contain six nested components: the main view, a row card for "my groups," a row card for "discover groups," a create group sheet, a compact leaderboard, and leaderboard rows. Each needed updating. Each had its own data dependencies.

The `NotificationsView` revealed assumptions that worked with mock data but failed with real data. The mock returned 10 notifications. Always. The real API returns pages of 20, with pagination for more. Suddenly I needed:

- Loading states for initial fetch
- Loading indicators for pagination
- Logic to detect when to fetch more (when the user scrolls near the bottom)
- Deduplication in case the same notification appears in multiple pages

What started as "swap MockDataService for InAppNotificationService" became an afternoon of careful work.

## The Review: Finding What Broke

After the initial migration, I did a thorough code review. What seemed like finished work had twenty-three issues across seven files:

**Two critical bugs:** GroupSettingsView silently dismissed instead of showing an error. GroupDetailView didn't navigate away after leaving a group, leaving users on a detail page for a group they no longer belonged to.

**Five high-priority issues:** Pagination could fire multiple times rapidly. Task cancellation wasn't properly checked after API calls. Data from one group could appear while viewing another. Search results weren't being deduplicated.

**Sixteen medium and low issues:** Missing error alerts. Form initialization timing. Accessibility hints. Empty state handling.

This is the part of integration that's hard to estimate upfront. The code compiles. The happy path works. But the edges are rough, and production apps need smooth edges.

## The Patterns That Emerged

Working through the integration, certain patterns repeated:

### Service State Management

Every service ended up with a similar structure:

```swift
@Observable
@MainActor
final class SomeService {
    static let shared = SomeService()
    
    private(set) var data: [SomeModel] = []
    private(set) var isLoading = false
    private(set) var hasLoaded = false
    private(set) var error: SomeServiceError?
}
```

The `isLoading` flag shows spinners. The `hasLoaded` flag distinguishes "no data yet" from "data loaded, but empty." The `error` property stores the last error for display. This pattern repeated across eight services.

### Error Type Conversion

Each service has its own error enum that wraps `APIClientError`:

```swift
enum GroupServiceError: LocalizedError {
    case unauthorized
    case groupNotFound
    case alreadyMember
    case validationError(String)
    case networkError(String)
    case serverError(String)
    case unknown(String)
    
    static func fromAPIError(_ error: APIClientError) -> GroupServiceError {
        switch error {
        case .unauthorized:
            return .unauthorized
        case .apiError(let apiError):
            // Map backend error codes to specific cases
            switch apiError.error.code {
            case "NOT_FOUND":
                return .groupNotFound
            case "ALREADY_MEMBER":
                return .alreadyMember
            // ...
            }
        // ...
        }
    }
}
```

This lets views show contextual error messages. "Group not found" means something different than "Network error" means something different than "You're already a member."

### Task Identity for Data Freshness

A subtle bug appeared in list views: navigate to a user's profile, then navigate to a different user's profile, and you'd briefly see the first user's data. The issue was view recycling—SwiftUI reused the view, which still had the old data while the new data loaded.

The solution was using `.task(id:)`:

```swift
.task(id: userId) {
    guard lastLoadedUserId != userId else { return }
    await loadUser()
    lastLoadedUserId = userId
}
```

The `id` parameter tells SwiftUI to cancel the old task and start a new one when the identifier changes. Combined with tracking what was last loaded, this ensures fresh data for each entity.

### Atomic Updates for Race Conditions

Follow/unfollow had a subtle race condition. The code found a user in an array by index, then modified that index. But if another update happened between the find and the modify, the indices could shift, corrupting data.

The fix was using `map` for atomic updates:

```swift
searchResults = searchResults.map { user in
    guard user.id == userId else { return user }
    return APIPublicUser(
        // ... copy all fields ...
        isFollowing: true
    )
}
```

No index lookup. No window for race conditions. The entire array transforms in one operation.

## What MockDataService Taught Me

Looking back, `MockDataService` was both helpful and harmful.

Helpful: it let me build the entire UI without backend dependencies. Every screen worked. Every edge case was visible. The design matured without waiting for API work.

Harmful: it hid the complexity of real data. Mock data was always valid, always present, always the right shape. Real data has nulls, has missing fields, has unexpected values. Real data comes from a network that fails. Real data arrives slowly. Real data paginates.

The mock's simplicity created false confidence. "The UI works" meant "the UI works with perfect fake data." Making it work with imperfect real data was the actual integration work.

## Reflections on the Process

If I were advising someone facing a similar integration:

**Invest heavily in the networking layer.** It's boring work, but every shortcut there becomes a problem in every feature later. Proper error handling, token refresh, retry logic—build it once, build it right.

**Migrate incrementally.** Don't try to replace all mock data at once. One service, one view, one feature at a time. Verify each works before moving on.

**Review your own code harshly.** The bugs I found weren't obvious during implementation. They appeared when I deliberately looked for edge cases, race conditions, error states. Assume your first pass missed something.

**Track everything in state.** Loading flags, error states, "has loaded" flags—they feel like boilerplate until you need them. Then they're essential for a good user experience.

**Test with slow networks.** The simulator's network link conditioner is invaluable. What happens when requests take five seconds? Ten seconds? Thirty? Does the UI remain usable?
