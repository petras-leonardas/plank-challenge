# The Foundation of Trust: Why Authentication Couldn't Wait

**By Leo Bacevicius**

## Introduction

There's a temptation, when building any app, to defer the "boring" infrastructure work. Authentication feels like plumbing—essential but unglamorous. Nobody downloads a fitness app because it has beautiful login screens.

So when I started building the backend for Plank Challenge, I had a choice. I could prototype the exciting features first—the plank sync, the leaderboards, the social graph—and handle authentication "later." Or I could treat authentication as the literal foundation: nothing else gets built until users can securely prove who they are.

I chose the foundation approach. This is the story of why authentication became my first backend feature, and what I learned implementing three different login methods for an iOS fitness app.

## The Designer's Dilemma: Why Not Skip This?

Let me be honest about my initial instinct. As a designer, I wanted to work on the visible things. The plank timer animations were done. The progress charts looked beautiful. The streak system was working locally with mock data.

Adding "Sign in with Apple" felt like a detour. A necessary one, sure, but couldn't it wait until the core features were solid?

Here's what changed my thinking: I realized authentication isn't a feature you add to an app. It's the identity layer that every feature sits on top of.

Consider what happens without user accounts:

| Feature | Without Auth | With Auth |
|---------|--------------|-----------|
| Plank history | Stored on one device | Synced across all devices |
| Streak | Lost when you change phones | Permanent, tied to your identity |
| Groups | Impossible | You can join and be recognized |
| Leaderboards | Anonymous, meaningless | Your name, your achievement |
| Progress | Trapped in local storage | Backed up, recoverable |

The app I'd been building wasn't a single-device fitness timer. It was a connected experience—planks that sync, groups that compete, progress that persists. Without authentication, I didn't have a product. I had a prototype pretending to be one.

## Why Three Methods? The Psychology of Choice

Early in planning, I decided to support three authentication methods:

1. **Sign in with Apple**
2. **Sign in with Google**
3. **Email and Password**

This might seem like over-engineering for a plank app. Why not just use Apple Sign-In and call it done?

### Reducing Friction to Zero

Here's the insight that drove this decision: every additional step between "I want to try this app" and "I'm using this app" is a conversion killer. The moment someone has to think "wait, do I have a Google account? What's my password? Should I create a new account?" you've lost momentum.

By supporting all three methods, I ensure that virtually every user can sign in with one tap using an identity they already have:

| User Type | Preferred Method | Why |
|-----------|-----------------|-----|
| iPhone-native | Sign in with Apple | Built into iOS, no passwords |
| Google ecosystem | Sign in with Google | Uses their primary identity |
| Privacy-conscious | Email/Password | Full control, no third parties |
| Corporate users | Email/Password | Work accounts may restrict OAuth |

No user should ever need to create a new password just to log planks.

### App Store Compliance

There's also a practical reason. Apple requires that if you offer any social login (like Google), you must also offer Sign in with Apple. It's not optional—it's policy. By planning for both from the start, I avoided rework later.

## The Implementation Journey

With the "why" established, I needed to actually build this. As a designer-learning-to-code, authentication felt intimidating. There's cryptography involved. Tokens. JWTs. Things that, if done wrong, expose user data.

I broke it down into manageable pieces.

### Understanding the Flow

Before writing code, I needed to understand what actually happens when someone taps "Sign in with Apple":

```
1. User taps "Sign in with Apple" in iOS app
2. iOS shows the Apple authentication sheet
3. User authenticates with Face ID / Touch ID / Password
4. Apple returns an identity token (a signed JWT)
5. iOS app sends this token to my backend
6. Backend verifies the token's signature using Apple's public keys
7. Backend extracts the user's email and Apple ID
8. Backend creates or updates the user account
9. Backend generates its own JWT tokens (access + refresh)
10. iOS app stores these tokens securely in Keychain
11. All future API calls include the access token
```

The critical insight: my backend doesn't trust the iOS app directly. It trusts Apple. The identity token is cryptographically signed by Apple, and my backend verifies that signature before doing anything.

This is why I couldn't use shortcuts. If I'd just accepted whatever the iOS app sent without verification, anyone could forge tokens and impersonate users.

### The Verification Challenge

Here's where things got technical—and where I learned the most.

Apple and Google both use a system called JWKS (JSON Web Key Sets). Instead of sharing a static secret, they publish their public keys at well-known URLs:

- Apple: `https://appleid.apple.com/auth/keys`
- Google: `https://www.googleapis.com/oauth2/v3/certs`

My backend fetches these keys, uses them to verify the token's signature, and only then trusts the identity inside.

```typescript
// Simplified verification flow
const jwks = createRemoteJWKSet(new URL('https://appleid.apple.com/auth/keys'));

const { payload } = await jwtVerify(identityToken, jwks, {
  issuer: 'https://appleid.apple.com',
  audience: 'com.leobacevicius.plankchallenge', // My Bundle ID
});

// Now I can trust payload.email and payload.sub (Apple ID)
```

This pattern—fetching public keys, verifying signatures—is the same for both Apple and Google. Once I understood it for one, implementing the other was straightforward.

### The Password Problem

Email/password authentication presented its own challenge: how do you store passwords securely?

The answer is hashing—storing a one-way transformation of the password, not the password itself. Even if someone stole my database, they couldn't recover the original passwords.

But here's what I discovered: the "standard" hashing algorithm (Argon2) doesn't work in Cloudflare Workers. It requires native code that edge environments don't support.

I had to use PBKDF2 instead—still secure, but different from what most tutorials recommend. This is the kind of friction you encounter building on newer platforms. The ecosystem is great, but sometimes you need to adapt patterns designed for traditional servers.

```typescript
// Password hashing using Web Crypto API (works in Workers)
const encoder = new TextEncoder();
const keyMaterial = await crypto.subtle.importKey(
  'raw',
  encoder.encode(password),
  'PBKDF2',
  false,
  ['deriveBits']
);

const hash = await crypto.subtle.deriveBits(
  {
    name: 'PBKDF2',
    salt: encoder.encode(salt),
    iterations: 100000,
    hash: 'SHA-256',
  },
  keyMaterial,
  256
);
```

## Security Beyond Authentication

Once users could authenticate, I needed to think about what happens next. Authentication is just the first line of defense.

### Rate Limiting: Stopping Brute Force

A malicious actor could try thousands of passwords per second, eventually guessing the right one. To prevent this, I implemented rate limiting with escalating blocks:

| Endpoint | Limit | Block Duration |
|----------|-------|----------------|
| Login attempts | 5 per minute | 5 minutes |
| Registration | 5 per hour | 1 hour |
| Password reset | 3 per hour | 1 hour |
| Apple/Google sign-in | 10 per minute | 5 minutes |

After 5 failed logins, you're locked out for 5 minutes. It's a small inconvenience for legitimate users who mistyped their password, but it makes brute force attacks impractical.

### Token Lifecycle: Access vs. Refresh

I implemented a two-token system:

- **Access Token**: Short-lived (1 hour), used for API requests
- **Refresh Token**: Long-lived (30 days), used to get new access tokens

Why this complexity? If someone steals an access token, they can only impersonate the user for an hour. The refresh token is stored more securely and can be revoked instantly if compromised.

### GDPR-Compliant Deletion

Here's something I didn't anticipate: the right to be forgotten. When a user deletes their account, I need to remove everything—not just mark it as deleted, but actually delete it.

This required a "hard delete" function that cascades through:
- All plank sessions
- All earned badges
- Group memberships (updating member counts)
- Follow relationships (updating follower counts)
- Notifications
- Device registrations
- The user record itself

Building this early, while the schema was simple, was far easier than retrofitting it later with more complex relationships.

## The Designer's Perspective: What I Learned

Building authentication taught me things that pure design work never could:

### 1. Security is UX

Bad security isn't just a technical failure—it's a user experience failure. If someone's account gets hacked, if their plank history is exposed, if they need to create yet another password, that's a negative experience that no beautiful animation can offset.

Good security, paradoxically, is invisible. Users tap "Sign in with Apple," see their name appear, and start planking. The cryptographic verification happening behind the scenes should be completely seamless.

### 2. Infrastructure Enables Features

Every feature I want to build—sync, groups, leaderboards—depends on knowing who the user is. By investing in solid authentication first, I've created a foundation where these features can be implemented cleanly.

If I'd hacked together authentication later, I'd probably have built features that worked around its limitations. Starting with the foundation meant starting with clarity.

### 3. Three Days Well Spent

Authentication took about three full days of work:
- Day 1: Research, understanding JWT, designing the flow
- Day 2: Implementing email auth, password hashing, token generation
- Day 3: Apple and Google verification, rate limiting, testing

It felt slow at the time. I wasn't shipping visible features. But those three days bought me confidence that everything built on top would be solid.

## What's Next

With authentication complete, I can finally build the features I've been eager to implement:

- **Plank Sync**: Recording planks that persist across devices
- **Streak Calculation**: Server-side validation of your longest streak
- **Groups**: Creating and joining plank challenges with friends
- **Leaderboards**: Competing on global and friend-based rankings

Each of these features assumes a known, authenticated user. Each would have been impossible—or insecure—without the foundation I've just laid.

The plumbing is done. Now comes the house.
