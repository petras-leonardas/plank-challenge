# The Invisible Work: Auditing and Standardising a Design System

*Why I stopped adding features and spent a week making the app consistent with itself*

---

There's a particular kind of technical debt that's easy to ignore because it doesn't break anything. The app builds. The tests pass. Users can do everything they're supposed to do. And yet something is subtly off.

A card here has `cornerRadius: 10`. The next card has `cornerRadius: 12`. One button is a filled Capsule; another is a stroked RoundedRectangle with radius 20. The leaderboard ranks silver as `.gray` in one file and `Color(red: 192/255, green: 192/255, blue: 192/255)` in another—literally the same colour, expressed two different ways, in two different files, with no connection between them.

None of these are bugs. But they accumulate. They make the codebase harder to change, because changing "the card radius" means hunting for every place a card radius is written instead of updating a single token. They make the visual design incoherent in ways users feel without being able to articulate. And they become significantly harder to fix the longer you leave them.

After completing the backend integration, Plank Challenge had all its features working. It was a good moment to stop and ask: before we ship, does the app look like it was made by one person with a clear vision, or does it look like twelve separate decisions that happened to end up in the same binary?

The honest answer was somewhere in between. This is what I did about it.

## What a Design System Audit Actually Means

When designers talk about design system audits, they mean cataloguing all the visual decisions in a product and identifying where they're inconsistent. When developers inherit that audit, they translate it into code changes.

I was doing both roles. My audit had to answer:

- **What tokens do we have?** Named colours, spacing values, corner radii, typography scales.
- **Where are we using literals instead of tokens?** Hardcoded `Color(red: 205/255, green: 127/255, blue: 50/255)` instead of `Color.rankBronze`.
- **Which components are duplicated?** Three nearly-identical badge views. Two inline "loading spinner + label" patterns. Five buttons that do the same thing but are written differently.
- **Where do structural patterns not exist yet?** Seven files with the identical `toolbarBackground(Color.subtleBlueGradientStart.opacity(0.5), for: .navigationBar)` line copied and pasted.

The audit produced a list of 47 distinct issues across 19 files. Not bugs. Not features. Just inconsistencies.

## Why Now

The temptation is always to defer this work. There are features to add. Users to get. Why spend a week making internal code more consistent when nobody can see it?

A few reasons convinced me it mattered before launch rather than after:

**Inconsistencies compound.** Every new screen built on an inconsistent foundation inherits the inconsistency. If `cardRadius` is sometimes 10 and sometimes 12, the next developer (future me) writing a new screen picks one at random, adding another datapoint to the chaos. Fix it once before there are 30 screens instead of 15.

**Tokens are a forcing function for design decisions.** The act of defining `Color.rankBronze` is also the act of deciding: this is our bronze colour, it is `Color(red: 205/255, green: 127/255, blue: 50/255)`, it will be this everywhere, forever, until we decide to change it. That's a real design decision. Making it explicit in code forces you to make it intentionally.

**Design system work is cheap now, expensive later.** Before launch, changing a component requires testing one app. After launch, with users and App Store reviews and update cycles, every visual change carries more weight. The window for "let's clean this up" is now.

**It visually matters, even if users can't name it.** Users notice when an app feels polished. They can't always say why—they'd never say "the card corner radii are inconsistent"—but they feel it as trust. Polished apps feel more reliable. Rough edges suggest the whole thing might be rough.

## The Token System

The existing codebase had a good start: a `Constants.swift` file with a `UI` enum and a `ViewExtensions.swift` with named colours. But the coverage was incomplete, and the coverage gaps were where the inconsistencies lived.

The first pass was purely additive. I extended `Constants.UI` with everything that was missing:

```swift
enum UI {
    // Spacing
    static let screenPadding: CGFloat = 16
    static let cardPadding: CGFloat = 16
    static let cardPaddingCompact: CGFloat = 12
    static let sectionSpacing: CGFloat = 24
    static let itemSpacing: CGFloat = 8
    static let itemSpacingMedium: CGFloat = 12
    
    // Corner Radius
    static let cardRadius: CGFloat = 12
    static let sheetRadius: CGFloat = 16  // modals, onboarding cards
    
    // Avatar Sizes
    static let avatarXSmall: CGFloat = 28
    static let avatarSmall: CGFloat = 32
    static let avatarMedium: CGFloat = 44
    static let avatarLarge: CGFloat = 72
    static let avatarXLarge: CGFloat = 80  // other users' profile pages
    
    // Misc
    static let appIconSize: CGFloat = 80
}
```

And extended the colour tokens:

```swift
// Rank colors (previously defined inline with hex literals)
static let rankGold = Color.yellow
static let rankSilver = Color(red: 192/255, green: 192/255, blue: 192/255)
static let rankBronze = Color(red: 205/255, green: 127/255, blue: 50/255)

// Semantic overlay
static let overlayScrim = Color.black.opacity(0.3)

// Stat card background
static let statCardBackground = Color(red: 240/255, green: 245/255, blue: 251/255)
```

These don't change anything visual. They give names to things that already existed. But naming is the first step to controlling.

## The `.appCardStyle()` Story

The single most-repeated inconsistency was the card style. An iOS card—a white rounded rectangle with a subtle shadow—appeared everywhere in the app: stat sections, leaderboard sections, group rows, calendar view, profile sections, user profile headers. Across all these locations, the card was written like this:

```swift
.padding(16)
.background(Color.warmWhiteCard)
.clipShape(RoundedRectangle(cornerRadius: 12))
.shadow(color: Color.black.opacity(0.04), radius: 8, x: 0, y: 2)
```

Four modifiers. Every time. For the same visual result. A `ViewModifier` called `.appCardStyle()` already existed—it was just being ignored.

The first audit pass missed some instances because it was auditing views that hadn't been looked at yet. The second pass found ten more sites across `GroupsView`, `GroupDetailView`, `UserProfileView`, and `StreakCalendarView` still writing the card style by hand.

The fix in each case was the same. Replace four lines with one:

```swift
.appCardStyle()
```

On its own, this is a cosmetic refactor. Its real value is that when we decide to adjust the card style—maybe the shadow should be slightly stronger, maybe the radius should go to 14 to feel more contemporary—we change one place and it propagates everywhere. Without this, we'd be hunting through twenty files trying to remember every card we ever wrote.

## Unifying What Was Split

The most interesting work was identifying components that should have been one thing but were several.

### The Three Badge Views

The app had three different ways to display a badge:

- `BadgesGridBadgeView`: 70px circle, 32pt emoji, shows progress bar for locked badges
- `APIBadgeView`: 60px circle, 28pt emoji, shows progress bar if progress > 0
- `ProfileAPIBadgeView`: 56px circle, 24pt emoji, earned-only (no progress)

All three displayed the same information—a badge emoji, a name, and optionally a progress indicator—just at different sizes. The inconsistency wasn't just visual (why are the circles 56, 60, and 70?) but structural: any change to badge display logic required updating three files instead of one.

The solution was a `BadgeViewSize` enum and a unified `APIBadgeDisplayView`:

```swift
enum BadgeViewSize {
    case small   // ProfileView horizontal scroll — 56px
    case medium  // ProgressView horizontal scroll — 60px
    case large   // BadgesView grid — 70px, includes progress label

    var circleSize: CGFloat { ... }
    var emojiSize: CGFloat { ... }
    var showsProgress: Bool { ... }
}

struct APIBadgeDisplayView: View {
    let badge: APIBadgeWithProgress
    var size: BadgeViewSize = .medium
    
    // Single implementation for all three use cases
}
```

The old structs were deleted. The call sites became `APIBadgeDisplayView(badge: badge, size: .large)` and `APIBadgeDisplayView(badge: badge, size: .medium)`. One component, three sizes, zero duplication.

### The Three Stat Components

Something similar had happened with stat display. Three components showed numbers with labels:

- `StatCard` (in `ProgressView`): full-width, left-aligned, 34pt value
- `StatBox` (in `ProfileView`): compact, centered, 3-up grid tile
- `MiniStatCard` (in `StreakStatsRow`): horizontal row with icon + value + label

All three were doing the same job—displaying a labelled number—at different sizes with different layouts. And all three were defined separately, with separate styling decisions that had quietly drifted apart (`StatBox` had `cornerRadius: 10`, not 12; `MiniStatCard` had `padding: 12` not 16).

The unified `StatCard` takes a `style` parameter:

```swift
enum StatCardStyle { case card, grid, mini }

struct StatCard: View {
    let title: String
    let value: String
    let icon: String?
    let color: Color
    let style: StatCardStyle
    
    var body: some View {
        switch style {
        case .card: cardLayout   // Full-width, ProgressView
        case .grid: gridLayout   // 3-up grid, ProfileView
        case .mini: miniLayout   // Horizontal row, StreakStatsRow
        }
    }
}
```

The old `StatBox` struct (which also had `cornerRadius: 10`—the only card-adjacent element in the app not using the standard 12) was deleted from `ProfileView.swift`. The corner radius is now 12 everywhere.

### The Five-File Navigation Bar Pattern

One of the more egregious examples of duplication was this line:

```swift
.toolbarBackground(Color.subtleBlueGradientStart.opacity(0.5), for: .navigationBar)
```

It appeared in `ProfileView`, `ProgressView`, `BadgesView`, `GroupsView`, `GroupDetailView`, `UserProfileView`, and `MyGroupsListView`. Seven files. Identical line. No shared definition.

The fix was a single `View` extension:

```swift
extension View {
    func appNavigationBarStyle() -> some View {
        self.toolbarBackground(Color.subtleBlueGradientStart.opacity(0.5), for: .navigationBar)
    }
}
```

Seven files now call `.appNavigationBarStyle()`. If we ever change the navigation bar tint—and at some point we will, because apps evolve—it changes in one place.

## Standardising Section Headers

The app had two competing section header styles. Views in the `Components` folder (like `ProgressView`) used `SectionHeader` with Title-Case `.headline` text. Views written later (`ProfileView`, `GroupsView`) wrote inline headers using ALL-CAPS `.caption` text:

```swift
// In SectionHeader component:
Text(title)
    .font(.headline)

// Inline in ProfileView:
Text("YOUR STATS")
    .font(.caption)
    .fontWeight(.semibold)
    .foregroundStyle(.secondary)
```

The ALL-CAPS caption style is the iOS native convention—it's how `List` section headers look throughout the system. It was the right call. The `SectionHeader` component was updated to match, and all inline header patterns were replaced with the component.

The component was also renamed from `SectionHeader` to `AppSectionHeader`. This turned out to be important: the Swift type checker, in certain compilation batches, would confuse `SectionHeader(title: "Danger Zone") { }` with SwiftUI's `Section("Danger Zone") { }`, causing cascading type errors in unrelated files. Naming it `AppSectionHeader` made it unambiguous.

## The Colour Audit

After the structural work, the colour audit was comparatively mechanical. I went through every file and replaced raw colour literals with their named tokens:

| Raw literal | Named token |
|-------------|-------------|
| `.cyan` | `Color.tealAccent` |
| `.orange` | `Color.streakColor` |
| `.red` | `Color.errorColor` |
| `.orange` (warning context) | `Color.warningColor` |
| `.green` | `Color.successColor` |
| `Color(red: 192/255, ...)` | `Color.rankSilver` |
| `Color(red: 205/255, ...)` | `Color.rankBronze` |
| `Color.black.opacity(0.3)` | `Color.overlayScrim` |

Some of these feel trivial. `.orange` → `Color.streakColor`—both are orange, so what's the difference? The difference is intention. `Color.streakColor` communicates *why* this element is orange: it represents streaks, and streaks are our orange. If we ever decide streaks should be amber, or coral, or a gradient, we change one token and every streak-related element updates. Raw `.orange` means hunting through every file asking "is this orange because it's a streak, or for some other reason?"

The `NotificationsView.iconColor` was a good example of where this mattered:

```swift
// Before:
switch displayType {
case .badgeEarned, .tokenEarned:   return .yellow
case .streakFreezeUsed:            return .cyan
case .groupJoined, ...:            return .green
case .groupRemoved, ...:           return .red
}

// After:
switch displayType {
case .badgeEarned, .tokenEarned:   return Color.warningColor
case .streakFreezeUsed:            return Color.tealAccent
case .groupJoined, ...:            return Color.successColor
case .groupRemoved, ...:           return Color.errorColor
}
```

Now the colours are semantically labelled. A reader of this code understands immediately that badge notifications use the "warning" palette (gold/yellow for achievement), group removal uses the "error" palette (red for negative action).

## Button Standardisation

The app had accumulated five different ways to render interactive buttons that all behaved the same way—a filled or outlined pill that taps to trigger an action:

1. `PillButtonStyle` in `ButtonStyles.swift` (the correct approach)
2. `RoundedRectangle(cornerRadius: 20).stroke(...)` in `ProfileView` (Edit Profile)
3. `Capsule().fill(Color.appAccent)` in `GroupsView` (Create Group)
4. Inline Capsule with `.foregroundColor()` in `UserRowView` (Follow/Unfollow)
5. Inline Capsule in `UserProfileView` (Follow/Unfollow)

The deprecated `.foregroundColor()` on the `UserRowView` button was a particular tell—it had never been updated to `.foregroundStyle()`, which suggests it was written once and not touched since.

All five were replaced with `.pillButtonStyle(isSelected:)`. The `UserProfileView` follow button was the trickiest, because it contained a loading spinner and used a fixed-width ghost `Text("Following")` to prevent layout shifts when the label changed. The inner layout was kept intact; only the outer styling was replaced.

I also added an `OnboardingPrimaryButtonStyle`—the white-background, accent-foreground, 56pt-height button that appeared identically in all three onboarding screens. One ButtonStyle definition, three call sites.

```swift
struct OnboardingPrimaryButtonStyle: ButtonStyle {
    func makeBody(configuration: Configuration) -> some View {
        configuration.label
            .font(.headline)
            .fontWeight(.semibold)
            .foregroundStyle(Color.appAccent)
            .frame(maxWidth: .infinity)
            .frame(height: 56)
            .background(.white)
            .clipShape(RoundedRectangle(cornerRadius: Constants.UI.sheetRadius))
            .opacity(configuration.isPressed ? 0.9 : 1.0)
            .scaleEffect(configuration.isPressed ? 0.98 : 1.0)
            .animation(.easeInOut(duration: 0.1), value: configuration.isPressed)
    }
}
```

## The Avatar Component Gets URL Support

`AvatarView` was a good component that had one gap: it only loaded images by local asset name, not by URL. This meant that every place in the app that displayed a remote profile photo had to bypass `AvatarView` entirely and implement its own `AsyncImage` block.

Three places did this:
- `ProfileView` (your own profile photo)
- `LeaderboardView` `APILeaderboardRow` (other users in leaderboard)
- `SearchView` `SuggestedUserRow` (suggested users)

And worse, several places that *should* have been showing profile photos were passing `imageName: nil` to `AvatarView`, silently falling back to initials even when a URL was available:
- `GroupDetailView` member avatars
- `GroupDetailView` leaderboard row avatars
- `UserProfileView` profile header

Adding URL support to `AvatarView` was a small change with outsized impact:

```swift
init(
    text: String,
    imageName: String? = nil,
    imageUrl: String? = nil,  // new
    size: CGFloat,
    style: AvatarStyle = .standard
) { ... }

var body: some View {
    if let urlString = imageUrl, let url = URL(string: urlString) {
        AsyncImage(url: url) { phase in
            switch phase {
            case .success(let image): image.resizable().scaledToFill()
            case .failure, .empty:   initialsView
            @unknown default:        initialsView
            }
        }
        .frame(width: size, height: size)
        .clipShape(Circle())
    } else if let imageName = imageName, !imageName.isEmpty {
        // local asset fallback
    } else {
        initialsView
    }
}
```

Profile photos now display wherever they're available. The fallback to initials still works. Every avatar in the app goes through a single component.

## LoadingView and EmptyStateView

The most-repeated structural pattern across all screens was the loading state and empty state. Every list screen had something like:

```swift
VStack(spacing: 12) {
    ProgressView()
    Text("Loading notifications...")
        .font(.subheadline)
        .foregroundStyle(.secondary)
}
.frame(maxWidth: .infinity, maxHeight: .infinity)
```

And every empty list had:

```swift
VStack(spacing: 12) {
    Image(systemName: "bell.slash")
        .font(.largeTitle)
        .foregroundStyle(.secondary)
    Text("No notifications")
        .font(.headline)
    Text("You're all caught up!")
        .font(.subheadline)
        .foregroundStyle(.secondary)
}
.frame(maxWidth: .infinity, maxHeight: .infinity)
```

These appeared four or five times each, with slight variations in spacing and font choices. Two shared components replaced them:

```swift
// Before:
VStack(spacing: 12) {
    ProgressView()
    Text("Loading notifications...")
        .font(.subheadline)
        .foregroundStyle(.secondary)
}
.frame(maxWidth: .infinity, maxHeight: .infinity)

// After:
LoadingView("Loading notifications...")

// Before (empty state):
VStack { Image... Text... Text... }
    .frame(maxWidth: .infinity, maxHeight: .infinity)

// After:
EmptyStateView(
    icon: "bell.slash",
    title: "No notifications",
    message: "You're all caught up!"
)
```

`EmptyStateView` also supports an optional `actionLabel` and `action` closure for empty states that include a CTA—like "No groups yet" with a "Create Group" button.

## The Things That Surprised Me

**The dead code was invisible.** `PlankHistoryRow` and `PlankHistoryRowFull` were struct definitions in two files that weren't called anywhere. They had accumulated during the migration from mock data to API data, when the API versions (`APIPlankHistoryRow` and `APIPlankHistoryRowFull`) replaced them. Nobody deleted the originals. They just... sat there, silently. The audit found them; the compiler hadn't complained.

**The compiler ambiguity was real.** Naming our section header component `SectionHeader` turned out to cause genuine type-checker failures in certain compilation batches—the Swift compiler would occasionally confuse `SectionHeader("Danger Zone") { }` with SwiftUI's `Section("Danger Zone") { }`, causing cascade failures in unrelated views. Renaming it `AppSectionHeader` fixed it permanently. Generic types that share naming patterns with SwiftUI system types are asking for trouble.

**The formatter allocation was a real performance issue.** `ISO8601DateFormatter` appeared as a computed property in two different views—instantiated fresh on every call:

```swift
private var performedDate: Date {
    let formatter = ISO8601DateFormatter()  // allocated every time
    formatter.formatOptions = [.withInternetDateTime, .withFractionalSeconds]
    return formatter.date(from: session.performedAt) ?? Date()
}
```

`ISO8601DateFormatter` is expensive to allocate. In a list with 50 rows, each rendering multiple times, this creates hundreds of unnecessary allocations. The fix was a `private static let`—allocated once, reused forever.

**Colour semantics are surprisingly clarifying.** When I replaced `.orange` with `Color.streakColor`, I had to think: is this orange because it represents streaks, or for some other reason? In most cases, it was streaks—correct. But in `OnboardingNotificationsView`, there was a flame illustration using raw `.orange`. Replacing it with `Color.streakColor` made the intent explicit: the flame in the onboarding is orange *because it represents the streak habit we're asking users to build*. That's a design decision, now expressed in code.

## What This Changes Going Forward

The audit work is invisible to users. They won't notice that `rankBronze` is now a named token or that `LoadingView` is a shared component. What they might notice—over time, as the app grows—is that it feels consistent. That every screen feels like it belongs to the same product.

For developers (future me), the changes matter more concretely:

- Adding a new screen that needs a card? `.appCardStyle()`. Done.
- Need the streak colour? `Color.streakColor`. Done.
- Building an onboarding step? `OnboardingPrimaryButtonStyle`. Done.
- Need a loading state? `LoadingView("Loading...")`. Done.

The marginal cost of doing things correctly is now lower than the marginal cost of doing them by hand. That's the point of a design system. When the right way is also the easy way, developers default to consistency.

## On Timing

If I were starting over, I'd do this work earlier. Not at the very beginning—design systems built before the product is understood are premature—but certainly before building 15 screens. By the time you have 15 screens, you have enough of a foundation to see what's consistent and what isn't. You have enough repetition to know what deserves a token.

The right time for a first design system audit is probably when you have three or four complete screens and are about to build more. Do the audit then. Every subsequent screen is built on a clean foundation.

We did it later. But we did it before launch, which is the important thing. The app that ships will be internally consistent in a way the app-before-audit wasn't.

The invisible work matters. You just don't see it when it's done right.
