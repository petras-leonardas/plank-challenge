# From Figma to Code: Building a Living Design System in SwiftUI

**By Leo Bacevicius**

## Introduction

If you've followed my previous posts, you know I made an unconventional choice: building Plank Challenge directly in SwiftUI, without touching Figma first. No mockups. No component libraries in design tools. Just code.

This approach has been liberating in many ways, but it created a new problem. After weeks of rapid development, I had components scattered across dozens of files. Buttons here, cards there, custom badges somewhere else. I knew what I had built, but I couldn't see it all in one place.

I needed a design system. Not in Figma—in the app itself.

This is the story of how a designer who barely opens Figma anymore built a living, breathing component catalog directly in SwiftUI.

## The Problem: Components Without a Home

When you design in Figma, you naturally create component libraries. It's part of the workflow. You build a button, save it as a component, and it appears in your assets panel. You can browse everything you've created.

When you build directly in code, this doesn't happen automatically. Each component lives in its own Swift file, but there's no visual overview. No way to see all your buttons side by side. No way to compare your card styles at a glance.

I found myself doing something absurd: writing code, running the app, navigating to the specific screen where a component appeared, just to see how it looked. Then doing it again for a different component. And again.

This wasn't sustainable. I needed what web developers have had for years: something like Storybook, but for SwiftUI.

## The Insight: The App Already Runs

Here's what clicked for me: I don't need an external tool. The app already runs on a simulator. It already renders SwiftUI views. Why not build the design system browser as a screen within the app?

This approach has several advantages:

1. **Components render exactly as they will in production** — No translation layer, no approximation
2. **Interactive by default** — Buttons are tappable, toggles toggle, animations animate
3. **Always up to date** — The catalog shows whatever's currently in the codebase
4. **Zero external dependencies** — No npm packages, no build tools, no configuration

The disadvantage? It's only visible when running the app. But since I'm running the app constantly during development, this isn't really a problem.

## The Architecture: Showcases and Categories

I structured the design system as a simple navigation hierarchy:

```
DesignSystemCatalog (main entry point)
├── ColorsShowcase
├── TypographyShowcase
├── ButtonsShowcase
├── CardsShowcase
├── AvatarsShowcase
├── BadgesShowcase
├── ListRowsShowcase
└── AnimationsShowcase
```

Each showcase is a scrollable view containing multiple component examples. The main catalog provides navigation to each category.

The key insight was creating a reusable `ComponentShowcase` wrapper that handles the common structure:

```swift
struct ComponentShowcase<Content: View>: View {
    let title: String
    let description: String
    let code: String
    let content: Content
    
    var body: some View {
        VStack(alignment: .leading, spacing: 12) {
            // Title and description
            Text(title).font(.headline)
            Text(description).font(.caption).foregroundStyle(.secondary)
            
            // Live component preview
            content
            
            // Code snippet
            CodeSnippetView(code: code)
        }
        .padding()
        .background(Color(.systemBackground))
        .cornerRadius(12)
    }
}
```

This wrapper ensures every component in the catalog has:
- A clear name
- A brief description of what it does
- The actual component, live and interactive
- A code snippet showing how to use it

## The Implementation: Real Components, Real Code

The beauty of this approach is that showcases use the actual components from the app. No mocks, no simplified versions. Here's an example from `ButtonsShowcase`:

```swift
ComponentShowcase(
    "Primary Action Button",
    description: "Main call-to-action with gradient background",
    code: """
    Button("Start Plank") {
        // action
    }
    .buttonStyle(PrimaryActionButtonStyle())
    """
) {
    Button("Start Plank") { }
        .buttonStyle(PrimaryActionButtonStyle())
}
```

The component in the preview is identical to the component in the app. If I change `PrimaryActionButtonStyle`, the catalog updates automatically. There's no sync problem because there's nothing to sync.

## DEBUG-Only: Keeping Production Clean

One critical detail: the Design System tab only appears in debug builds.

```swift
#if DEBUG
Tab("Design", systemImage: "paintbrush") {
    NavigationStack {
        DesignSystemCatalog()
    }
}
#endif
```

Users downloading from the App Store will never see this tab. It's purely a development tool. This keeps the production app focused while giving me full access to the component library during development.

## What I Included: The Eight Categories

After auditing my codebase, I organized components into eight categories:

### 1. Colors
The app's color palette: brand colors, semantic colors (success, warning, error), and background variations. Each color shows its name, hex value, and a swatch.

### 2. Typography
Font styles used throughout the app. Large titles, body text, captions, button labels. Seeing them all together revealed some inconsistencies I hadn't noticed—and promptly fixed.

### 3. Buttons
Every button style: primary actions, secondary actions, destructive buttons, icon buttons, toggle buttons. Interactive, so you can tap them and see their pressed states.

### 4. Cards
The various card styles: stat cards, result cards, grouped list cards. This category made me realize I had three slightly different card backgrounds. Now I have one.

### 5. Avatars
User avatars in different sizes and styles: standard (colored background with initial), gradient (for the current user), and image-based (for users with photos).

### 6. Badges & Pills
Achievement badges (earned/unearned states), admin badges, generic pill badges, rank indicators, token displays. Small components that add up to a lot of visual language.

### 7. List Rows
User rows, leaderboard rows, settings rows. These are the building blocks of most screens in the app. Seeing them together ensured consistent spacing and alignment.

### 8. Animations
The fun category. Animated flames, lava bubbles, celebration rings, pulsing effects. Animations need to be seen in motion, so this category is particularly valuable—you can't evaluate animation timing from static code.

## The Unexpected Benefits

Building this catalog surfaced benefits I hadn't anticipated:

### Inconsistency Detection
When you see all your buttons in one place, inconsistencies jump out. "Why is this button 44pt and that one 48pt?" Seeing components side by side is the fastest way to find and fix these issues.

### Documentation That Can't Lie
Traditional documentation gets outdated. Someone changes a component but forgets to update the docs. With a live catalog, this can't happen. The documentation is the component.

### Onboarding Tool
If I ever bring another developer onto this project, I can point them to the Design tab. "This is our design language. Browse it." No lengthy documentation to write or maintain.

### Design Review Without Figma
I can screenshot the catalog views and share them with anyone for feedback. The screenshots show exactly what the app looks like because they are the app.

### Faster Iteration
Need to tweak a component? I can open the catalog, see all uses of that component, make changes, and immediately see results—without navigating through the app.

## A Designer's Reflection

I spent years in Figma. I built component libraries with auto-layout, variants, and property panels. I maintained design systems with hundreds of components and documented every possible state.

Building a design system in code feels different.

In Figma, a button is a drawing. It looks like a button, it has the right colors and borders, but it doesn't actually do anything. You're creating a representation.

In code, a button is a button. It has hover states because it actually hovers. It has animations because it actually animates. You're creating the thing itself.

This feels more honest somehow. There's no gap between design and implementation because they're the same artifact.

Of course, this approach has tradeoffs. I can't explore 20 color variations as quickly as I could in Figma. I can't share a link for stakeholder review as easily. The tools for visual exploration are less developed.

But for me, working alone on a focused app, the benefits outweigh the costs. I'm building exactly what users will experience, from the very first line of code.

## Industry Parallels

I was curious whether other teams work this way. Turns out, many do:

- **Airbnb** has internal component browsers for their native apps
- **Shopify's Polaris** includes mobile component explorers
- **Microsoft's Fluent UI** has in-app galleries
- Most large iOS teams have some form of component catalog, even if they're not public

On the web, **Storybook** is nearly universal. What I've built is essentially "Storybook for SwiftUI"—a component development environment that happens to live inside the app.

## Technical Notes

A few implementation details that might help others:

### Use ScrollView, Not List
List has nice default styling, but it fights you on layout. ScrollView with VStack gives you complete control over spacing and backgrounds.

### Code Snippets Need Monospace
```swift
Text(code)
    .font(.system(.caption, design: .monospaced))
    .padding(12)
    .background(Color(.systemGray6))
    .cornerRadius(8)
```

### Section Headers Add Structure
A simple `ShowcaseSectionHeader` component with an icon and title helps users navigate long showcase views.

### Keep Previews
Each showcase file includes `#Preview`. This means you can also access components through Xcode's canvas, not just the in-app tab.

## What's Next

The catalog is functional, but there's room to grow:

- **Search** — Find components by name
- **Filtering** — Show only buttons, only animations, etc.
- **State Controls** — Toggle component states (enabled/disabled, loading, error)
- **Theming** — Preview components in light/dark mode, different dynamic type sizes
- **Export** — Generate documentation or screenshots automatically

But even in its current form, the Design System catalog has changed how I work. I spend less time hunting for components and more time improving them. I catch inconsistencies earlier. I have confidence in my design language.

For a designer learning to build in code, that confidence is everything.
