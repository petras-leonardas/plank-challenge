# A Picture Is Worth a Thousand Bytes: Building the Media Upload System

**By Leo Bacevicius**

## Introduction

Profile pictures are one of those features that seem deceptively simple. You pick a photo, it shows up next to your name. Done.

Except it's never that simple.

Behind that tiny circular avatar is a chain of decisions about security, performance, storage costs, and user experience. How do you prevent someone from uploading a 50MB image that crashes the app? Where do you store it? How do you make sure it loads instantly on a slow connection? What happens when they want to change it?

Phase 4 of Plank Challenge was about building a media system that handles all of this invisibly. The user sees a simple "change photo" button. What they don't see is the careful architecture that makes that button work reliably.

## The Three Approaches to Image Upload

When I started researching how to handle image uploads with Cloudflare R2 (the object storage I'm using), I found three common patterns:

### Option 1: Two-Step Presigned URLs

This is the classic approach for cloud storage. The flow works like this:

1. Your app asks the server for permission to upload
2. Server generates a special URL that's valid for a few minutes
3. App uploads the image directly to cloud storage using that URL
4. App tells the server "I finished uploading"
5. Server verifies and updates the user profile

It's elegant because your server never handles the image bytes—they go straight from the phone to cloud storage. Great for scalability.

### Option 2: Direct Upload Through Server

The simpler approach:

1. App sends the image to your server
2. Server validates everything
3. Server uploads to cloud storage
4. Server updates the user profile
5. Server tells the app it's done

Your server handles every byte. Less scalable, but simpler to reason about.

### Option 3: Base64 in JSON

The approach that makes backend developers cringe:

1. App converts image to base64 string
2. App sends JSON with image embedded
3. Server decodes base64 and processes

Technically works, but inflates file size by ~33% and makes your API awkward.

## Why I Chose Option 2

For Plank Challenge, I went with direct upload through the server. Here's why:

**Authentication is simpler.** With presigned URLs, you need to set up S3-compatible credentials, manage their security, and potentially expose them in different ways. With direct upload, I use the same JWT authentication that protects every other endpoint. One auth system, everywhere.

**Validation happens before storage.** I can check file type and size before accepting any bytes. With presigned URLs, the upload happens first, then you validate. If someone uploads garbage, you've already paid for the storage write and now have to clean it up.

**Fewer moving parts.** One HTTP request instead of three. One thing that can go wrong instead of three. When you're building a fitness app and not a photo-sharing platform, simplicity wins.

**The math works out.** Plank Challenge profiles will have profile pictures, maybe group images. Not millions of photos. A Cloudflare Worker can handle streaming a 5MB image without breaking a sweat. If I was building Instagram, different story.

## What Could Go Wrong (And How I Prevented It)

Image uploads have a surprising number of edge cases. Here's my defensive checklist:

### The "Send Me Your Entire Hard Drive" Attack

Without size limits, someone could upload a 10GB file and exhaust server resources. I check the Content-Length header before accepting any data, and then double-check the actual byte count after receiving the data (because headers can lie).

**Limit:** 5MB per image. Plenty for a good-looking profile picture, not enough to cause trouble.

### The "Actually It's Not an Image" Problem

Just because someone sends a Content-Type of `image/jpeg` doesn't mean the file is actually a JPEG. I verify the content type header matches an allowed list: JPEG, PNG, or WebP. 

Could someone send a malicious file with a spoofed content type? In theory, yes. But since we're storing it in object storage and serving it with its original content type, there's no code execution risk. The worst case is someone stores a text file that claims to be an image—and when someone tries to load it, it just won't display.

### The "My Old Photo Is Still Showing" Cache Bug

When a user changes their profile picture, everyone should see the new one. But aggressive caching could show stale images for days.

My solution: every uploaded image gets a unique timestamp in its storage key. Your old avatar was `avatar_1710432000.jpg`, your new one is `avatar_1710518400.jpg`. Different URLs mean no cache confusion.

The trade-off: we need to delete old images to avoid accumulating storage. I handle this automatically—upload the new image, update the profile, then delete the old one.

### The "Where Did My Photo Go" Orphan Problem

What if the upload succeeds but the database update fails? Or vice versa? You end up with orphaned images in storage or database references to images that don't exist.

I structured the upload as a sequence: upload to R2 first, then update the database. If the upload fails, we never touch the database. If the database update fails after upload, we have a cleanup path—but this is the rare case, and I log it for monitoring.

## The Storage Structure That Scales

I organized R2 storage with a clear hierarchy:

```
plank-challenge-media/
├── profiles/
│   └── {userId}/
│       └── avatar_{timestamp}.jpg
├── groups/
│   └── {groupId}/
│       └── cover_{timestamp}.jpg
└── gallery/          (future)
    └── {userId}/
        └── {mediaId}.jpg
```

Each user has their own folder. Each image has a timestamp in its name. Future features like group images and photo galleries have reserved locations.

Why timestamps instead of just `avatar.jpg`? Two reasons:

1. **Cache busting** - A new timestamp means browsers request the fresh image
2. **Audit trail** - In logs, I can see exactly which version of an image was involved in any issue

## What I'm Storing in the Database

One decision that might seem minor but matters: I store the R2 key, not a full URL.

Instead of:
```
https://media.plankchallenge.app/profiles/abc123/avatar_1710432000.jpg
```

I store:
```
profiles/abc123/avatar_1710432000.jpg
```

Why? Flexibility. If I switch CDN providers, change domains, or need to serve images through a different path, I only update the code that constructs URLs—not every row in the database.

The profile endpoint constructs the full URL when responding. The storage is just the key.

## The Endpoint That Surprised Me

I built an endpoint I didn't initially plan: `GET /media/avatar/:userId`.

This lets anyone fetch a user's avatar by their ID. The server looks up the image key, streams it from R2, and adds appropriate caching headers.

Why is this useful when you could just use the stored URL? Because it gives me a stable URL that always returns the current avatar. Perfect for social features where other users see your profile picture. They don't need to know your image's timestamp—they just need to request your avatar.

Also useful: I can add image transformations later. Request `/media/avatar/:userId?size=100` and get a thumbnail. The foundation is there.

## What I Deferred

The original plan included automatic thumbnail generation. When you upload a profile picture, a background job would create a smaller version for lists and feeds.

I built the queue infrastructure but deferred the actual thumbnail generation. Here's my reasoning:

1. **It's not critical path.** Phones are fast at resizing images locally.
2. **It adds complexity.** Image processing in Workers requires WASM libraries.
3. **I can add it later.** The hook points exist. When thumbnail generation becomes important, I add a queue consumer.

This is the kind of decision that's easy to second-guess, but I'd rather ship a working feature now and enhance it based on real usage than delay shipping for a nice-to-have.

## For Designers: What This Means for the iOS App

If you're implementing the profile picture flow in the iOS app, here's what you need to know:

**Single request upload.** Compress the image locally (I recommend max 1024px on longest edge, JPEG at 80% quality), then POST the binary data to `/media/avatar` with the appropriate Content-Type header.

**Instant feedback.** The endpoint returns the new image URL immediately. Update the UI before the response even comes back—you already have the image locally.

**Stable avatar URLs.** To show another user's avatar, fetch `/media/avatar/{userId}`. This always returns their current avatar, with proper caching headers.

**Error handling.** Check for 400 errors (bad file) and 413 errors (too large). Show appropriate messages. "Please choose a smaller image" is friendlier than "VALIDATION_ERROR."

## Reflections: Simple Is Hard

The final implementation is about 400 lines of code across two files. It handles everything I outlined above. A user taps "change photo," picks an image, and sees their new avatar appear.

But those 400 lines represent a lot of decisions about what *not* to build. No presigned URL complexity. No thumbnail generation (yet). No fancy image transformations.

Every feature I didn't build is a feature that can't break, doesn't need testing, and won't confuse users. The art of software development is knowing what to leave out.

Profile pictures work. They work simply. They work reliably. That's enough for now.
