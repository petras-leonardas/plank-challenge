# Building the Sync Engine: From Theory to Working Code

**By Leo Bacevicius**

## Introduction

In my last post, I wrote about choosing a conflict resolution strategy for offline sync. I analyzed how apps like Strava, Apple Health, and Day One handle the problem. I concluded that for a plank tracking app, each workout is a unique event—no conflicts, just additions.

That was theory.

This post is about what happened when I actually built the thing. Spoiler: theory is clean; implementation is messy. I discovered timezone bugs that broke streak calculation, race conditions that could drain freeze tokens, and sync endpoints that could crash if you planked too enthusiastically.

These aren't failures—they're the reality of learning to code. And I'm documenting them because I wish someone had told me: the hard part isn't understanding concepts. It's the cascade of edge cases that appear the moment you deploy real code.

## The Timezone Bug That Almost Shipped

Here's the first version of my streak calculation. Can you spot the bug?

```sql
SELECT date(performed_at) as plank_date
FROM plank_sessions
WHERE user_id = ?
ORDER BY performed_at DESC
```

I grouped planks by date, sorted them, and counted consecutive days. It worked perfectly in my tests.

Then I realized: `date()` in SQLite extracts the date in UTC.

Picture this scenario:
- A user in New York planks at 10pm on January 15th (Eastern Time)
- The timestamp stored is `2024-01-16T03:00:00Z` (UTC)
- My query extracts `2024-01-16`
- The user thinks they planked on January 15th
- The server thinks they planked on January 16th

Now imagine this user planks again on January 16th at 8am Eastern. They've planked two consecutive days in their reality. But the server sees two planks on January 16th (UTC) and nothing on January 15th. Streak = 1 day, not 2.

### The Fix

Each plank already stores its timezone (`America/New_York`, `Europe/London`, etc.). The fix was to convert each timestamp to its local date before counting:

```typescript
function getPlankLocalDate(performedAt: string, timezone: string): string {
  const date = new Date(performedAt);
  const formatter = new Intl.DateTimeFormat('en-CA', {
    timeZone: timezone,
    year: 'numeric',
    month: '2-digit',
    day: '2-digit',
  });
  return formatter.format(date); // Returns "2024-01-15"
}
```

The query now fetches both `performed_at` AND `timezone`:

```typescript
const planks = await db
  .prepare(`
    SELECT performed_at, timezone
    FROM plank_sessions
    WHERE user_id = ? AND deleted_at IS NULL
    ORDER BY performed_at DESC
  `)
  .bind(userId)
  .all();

// Convert each plank to its local date
const plankDates = planks.results.map((p) => 
  getPlankLocalDate(p.performed_at, p.timezone || 'UTC')
);
```

This handles users who travel. If you plank in Tokyo on Monday and fly to San Francisco and plank again on Monday (which is still Sunday in Tokyo), you get credit for two days—because in your experience, you planked two different days.

### Lesson Learned

**Never trust date extraction in SQL for user-facing features.** The database doesn't know what timezone the user thinks they're in. Always convert timestamps to local dates in application code where you have timezone context.

## The Race Condition I Didn't See Coming

Freeze tokens let users skip a day without breaking their streak. The implementation seemed straightforward:

```typescript
// First version (buggy)
async function useFreezeToken(db, userId) {
  const user = await db.query('SELECT freeze_tokens FROM users WHERE id = ?', userId);
  
  if (user.freeze_tokens <= 0) {
    return { success: false, error: 'No tokens available' };
  }
  
  await db.query('UPDATE users SET freeze_tokens = freeze_tokens - 1 WHERE id = ?', userId);
  
  return { success: true, remaining: user.freeze_tokens - 1 };
}
```

Do you see the race condition?

If two requests arrive simultaneously:
1. Request A reads `freeze_tokens = 1`
2. Request B reads `freeze_tokens = 1`
3. Request A decrements: `freeze_tokens = 0`
4. Request B decrements: `freeze_tokens = -1`

Both requests succeeded. One token became negative one. The user just got a free freeze.

"But who would make two simultaneous requests?" you ask. A user frantically tapping the freeze button when the network is slow. A buggy iOS app that retries on timeout. Someone with a script testing your API.

### The Fix

The solution is an atomic UPDATE that includes the check in the WHERE clause:

```typescript
const result = await db
  .prepare(`
    UPDATE users SET
      freeze_tokens = freeze_tokens - 1,
      updated_at = ?
    WHERE id = ? AND freeze_tokens > 0 AND current_streak > 0
  `)
  .bind(new Date().toISOString(), userId)
  .run();

// Check if the update actually happened
if (result.meta.changes === 0) {
  // Either no tokens, no streak, or another request got there first
  return { success: false, error: 'Could not use freeze token' };
}
```

Now the check and the decrement happen in a single database operation. If two requests race, only one will successfully decrement—the other will see `changes === 0` and know it lost.

### Lesson Learned

**Any read-check-write sequence can race.** If you're checking a condition then updating based on it, another request can slip in between. The fix is always to make the check and update a single atomic operation.

## The Sync Endpoint That Could Crash

My first sync implementation returned all planks:

```typescript
planks.get('/sync', async (c) => {
  const userId = c.get('userId');
  const { since } = c.req.query();
  
  const planks = await db
    .prepare('SELECT * FROM plank_sessions WHERE user_id = ? AND updated_at > ?')
    .bind(userId, since || '1970-01-01')
    .all();
  
  return c.json({ planks: planks.results });
});
```

Works fine for most users. But what about someone who's been planking twice daily for a year? That's 730 planks. What if they delete the app and sync fresh? All 730 planks in one response.

Cloudflare Workers have memory limits and timeout limits. A massive response could exhaust memory. A slow client connection could cause timeouts. And worse—as the app grows, "power users" will have even more data.

### The Fix: Cursor-Based Pagination

Instead of returning everything, the endpoint now paginates:

```typescript
const syncPlanksSchema = z.object({
  since: z.string().datetime().optional(),
  limit: z.coerce.number().min(1).max(500).default(100),
  cursor: z.string().datetime().optional(),
});

planks.get('/sync', zValidator('query', syncPlanksSchema), async (c) => {
  const { since, limit, cursor } = c.req.valid('query');
  
  let query = `
    SELECT * FROM plank_sessions
    WHERE user_id = ?
  `;
  const params = [userId];
  
  if (since) {
    query += ` AND updated_at > ?`;
    params.push(since);
  }
  
  if (cursor) {
    query += ` AND updated_at > ?`;
    params.push(cursor);
  }
  
  query += ` ORDER BY updated_at ASC LIMIT ?`;
  params.push(limit + 1); // +1 to detect if there's more
  
  const results = await db.prepare(query).bind(...params).all();
  
  const hasMore = results.length > limit;
  const planksToReturn = hasMore ? results.slice(0, limit) : results;
  const nextCursor = hasMore ? planksToReturn[planksToReturn.length - 1].updated_at : null;
  
  return c.json({
    planks: planksToReturn,
    pagination: { hasMore, nextCursor, limit },
    serverTimestamp: new Date().toISOString(),
  });
});
```

The iOS app now syncs in batches:

1. `GET /planks/sync?limit=100` → returns 100 planks, `hasMore: true`, `nextCursor: "2024-03-14T10:00:00Z"`
2. `GET /planks/sync?limit=100&cursor=2024-03-14T10:00:00Z` → returns next 100 planks
3. Repeat until `hasMore: false`

### Why Cursor Pagination Over Offset?

You might wonder why I used a cursor (`updated_at`) instead of offset (`LIMIT 100 OFFSET 100`). 

Offset pagination has a problem: if new planks are inserted while paginating, you might miss items or see duplicates. Cursor pagination uses the last item's `updated_at` as a stable reference point. The query always returns items "after this timestamp," regardless of what was inserted.

### Lesson Learned

**Always paginate endpoints that return unbounded collections.** It doesn't matter if your test user has 5 planks. Assume someone will have 5,000 and design accordingly.

## Transaction Safety: Because Half-Complete Is Worse Than Not Started

Creating a plank involves two database operations:
1. Insert the plank record
2. Update the user's stats (total planks, total seconds, longest plank)

What happens if the insert succeeds but the stats update fails? The plank exists, but stats are wrong. The user sees their plank in the list but the totals are off.

### The Fix: D1 Batch

Cloudflare D1 provides `db.batch()` which executes multiple statements atomically:

```typescript
const batchResults = await db.batch([
  // Statement 1: Insert the plank
  db.prepare(`
    INSERT INTO plank_sessions (id, client_id, user_id, duration_seconds, ...)
    VALUES (?, ?, ?, ?, ...)
  `).bind(plankId, data.clientId, userId, data.durationSeconds, ...),
  
  // Statement 2: Update user stats
  db.prepare(`
    UPDATE users SET
      total_planks = ?,
      total_plank_seconds = ?,
      longest_plank_seconds = ?,
      updated_at = ?
    WHERE id = ?
  `).bind(newTotalPlanks, newTotalSeconds, newLongestPlank, now, userId),
]);

// Check for errors in batch
for (const result of batchResults) {
  if (!result.success) {
    return errors.serverError(c, 'Failed to create plank session');
  }
}
```

Either both succeed or both fail. No half-states.

### Lesson Learned

**Group related writes into transactions.** If operation B depends on operation A completing, they should be atomic. Database transactions exist precisely for this reason.

## The Bug That Made Me Read My Own Error Messages

While testing, I deleted a plank and got this response:

```json
{ "error": "Plank session not found not found" }
```

Double "not found." Embarrassing.

I traced it to my error helper:

```typescript
// In response.ts
export function notFound(c: Context, resource: string) {
  return c.json({ error: `${resource} not found` }, 404);
}

// In planks.ts
if (!plank) {
  return errors.notFound(c, 'Plank session not found');
}
```

The helper already appends "not found." I was passing "Plank session not found" and getting "Plank session not found not found."

### The Fix

```typescript
if (!plank) {
  return errors.notFound(c, 'Plank session');
}
// Now returns: "Plank session not found"
```

### Lesson Learned

**Read your own error messages.** Test unhappy paths. The embarrassing bugs are often the ones you never exercised.

## The Freeze Token Tracking Problem

After implementing freeze tokens, I realized a subtle issue. The streak calculation uses `last_plank_date` to determine if a streak is active. When a user freezes, I update `last_plank_date` to today.

But now I can't tell the difference between:
- User planked today → `last_plank_date` = today
- User used freeze today → `last_plank_date` = today

Why does this matter? The UI needs to know. "You've planked today!" is different from "Streak protected with freeze!" The badges should probably differ too.

### The Fix: Add `last_freeze_date`

I added a new column to track when a freeze was last used:

```sql
ALTER TABLE users ADD COLUMN last_freeze_date TEXT;
```

Now when a user freezes:
```typescript
await db
  .prepare(`
    UPDATE users SET
      last_plank_date = ?,
      last_freeze_date = ?,
      updated_at = ?
    WHERE id = ?
  `)
  .bind(today, today, now, userId)
  .run();
```

The API response now includes distinct flags:

```json
{
  "hasPlankkedToday": false,
  "usedFreezeToday": true,
  "streakProtectedToday": true
}
```

### Lesson Learned

**Think about what state you need to reconstruct later.** If two different actions result in the same database state, you can't tell them apart. Add tracking fields when the distinction matters.

## The Designer's Reflection

Building Phase 2 felt different from Phase 1 (authentication). Auth was about understanding security concepts—JWT, OAuth, cryptographic verification. Phase 2 was about operational correctness—making sure the system behaves correctly under all conditions.

### 1. Edge Cases Are The Real Work

The "happy path" took maybe 20% of the time. The other 80% was handling:
- What if the timezone is invalid?
- What if someone syncs with 10,000 planks?
- What if two requests race?
- What if the user is near midnight?

These aren't exotic scenarios. They're Tuesday afternoon when your app has real users.

### 2. The Audit Changed Everything

Midway through, I reviewed my own code with fresh eyes. I found the timezone bug, the race condition, the pagination issue—all in code I'd written days earlier and thought was complete.

If I'd shipped without that review, users would have found the bugs for me. With their broken streaks. On their devices.

### 3. Documentation is Future You's Best Friend

Every time I fixed a bug, I added a comment explaining why. Future me (or future contributors) will thank present me for notes like:

```typescript
/**
 * CRITICAL FIX: We now fetch both performed_at and timezone for each plank,
 * then convert to local dates using each plank's timezone. This handles:
 * - Users in different timezones
 * - Users who travel and plank in different timezones
 * - Edge cases around midnight UTC
 */
```
