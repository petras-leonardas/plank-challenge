# The Right Nudge at the Right Time: Building Smart Push Notifications

*Why we threw away our working notification system and rebuilt it from the server*

---

There's a moment during development where something works and you're tempted to move on. The daily reminder feature worked. The user picked a time during onboarding, iOS scheduled a repeating notification, and every day at that time their phone would buzz with "Time to plank." Feature complete. Ship it.

Except I kept noticing something that bothered me. I'd complete my plank at 3pm, feel good about it, and then at 7pm my phone would remind me to plank. The thing I'd already done. Every single day.

It wasn't broken. It was just dumb. The notification had no idea whether I'd planked or not. It fired unconditionally, every day, forever, because that's what local notifications do. And every time it fired unnecessarily, it taught me to ignore it a little more.

That's the problem with notifications that cry wolf. They erode trust. The tenth unnecessary reminder doesn't feel like a helpful nudge -- it feels like spam from your own app.

## How Local Notifications Actually Work

Before I explain what we changed, it helps to understand what was there before.

iOS has a built-in system called `UNCalendarNotificationTrigger`. You tell it "send this notification every day at 7pm" and it does exactly that. No server involved. No internet required. The phone handles everything locally.

This is elegant for simple cases. Set a daily alarm. Remind someone about a meeting. Fire and forget.

But local notifications have a fundamental limitation: they can't think. Once scheduled, they fire unconditionally. There's no callback before delivery where you can check a condition and decide "actually, skip this one." The notification is a pre-recorded message, not a live decision.

I looked into workarounds. Cancel the notification after each plank, then reschedule it the next morning. But that requires the app to open every day to re-arm the notification -- and if the user doesn't open the app on a given day, they'd get no reminder on the one day they actually need it.

## How Apps Like Duolingo Solve This

I started researching how other habit-tracking apps handle this, and the answer was immediately obvious once I saw it.

Duolingo doesn't schedule local notifications. Their server sends you a push notification. And before it sends, it checks: has this user completed their lesson today? If yes, it skips the notification silently. If no, it sends the reminder.

The decision happens on the server, at the moment of sending, with full knowledge of the user's current state. The server knows whether you've planked today because it has the database right there. It doesn't need to ask the phone. It doesn't need the app to be open. It just knows.

This is the difference between a dumb alarm clock and an intelligent assistant. The alarm goes off at 7am regardless of whether it's a weekday or you're on holiday. The assistant checks your calendar first.

## What We Actually Built

The implementation has four layers, each one building on the last.

### Storing the Preference

First, the backend needed to know when each user wants their reminder. We added two columns to the user database: `reminder_enabled` (on/off) and `reminder_time` (the time as "HH:mm", like "19:00" for 7pm). When a user sets their reminder during onboarding or changes it in Settings, the app saves the preference locally and syncs it to the backend.

This was the simplest part. A database migration, a couple of new fields on the API, and some plumbing in the iOS app to send the data up.

### Sending Visible Notifications

Our backend could already send push notifications to iPhones -- but only the invisible kind. Silent pushes that wake the app in the background to sync fresh data. No banner, no sound, no user-visible indication.

For reminders, we needed the other kind: a banner that slides down from the top of the screen with a title and a message. Same delivery mechanism (Apple's Push Notification service), but a different payload shape and priority level. Silent pushes are low-priority background tasks. Alert pushes are high-priority and delivered immediately.

We added a new function alongside the existing one. Same authentication, same device token lookup, same stale-token cleanup -- just a different payload that says "show this to the user" instead of "quietly wake the app."

### The Scheduled Job

This is where the intelligence lives. A scheduled job runs on our server every five minutes. Each time it runs, it:

1. Finds all users who have reminders enabled and have at least one device registered
2. For each user, converts the current time to their timezone
3. Checks whether their chosen reminder time falls within the current five-minute window
4. Checks whether they've already planked today
5. Checks whether we've already sent them a reminder today (to avoid duplicates)
6. If all conditions pass, sends the push notification

That fourth check is the entire point. If `last_plank_date` equals today's date in the user's timezone, we skip them. No unnecessary notification. No crying wolf.

The five-minute interval means a user's reminder might arrive up to four minutes after their chosen time. We considered running every minute for tighter precision, but the difference between "exactly 7:00pm" and "sometime between 7:00 and 7:04pm" is imperceptible for a daily habit reminder. The tradeoff -- five times fewer server executions -- was worth it.

### Timezone Awareness

This part was more nuanced than I expected. Our server runs on Cloudflare Workers, which operate in UTC. But users live in timezones. A user in Tokyo who sets a 7pm reminder needs their notification at 7pm JST, not 7pm UTC (which would be 4am in Tokyo).

Every user has a timezone stored in their profile. When the cron job runs, it converts "right now" into each user's local time, then checks whether that local time matches their reminder window. A user in UTC+9 and a user in UTC-5 can both have "19:00" as their reminder time, and each will receive it at their local 7pm.

## What We Removed

Once server-side notifications were working, we stripped out all the local notification scheduling code from the iOS app. The app no longer schedules any `UNCalendarNotificationTrigger`. It doesn't need to. The server handles everything.

The app still does two things related to notifications:

**Permission request.** iOS requires the app to ask the user for notification permission. This happens during onboarding or when they enable reminders in Settings. Without this permission, the server can send all the pushes it wants -- the phone will silently discard them.

**Tap handling.** When a user taps the notification banner, we navigate them directly to the Plank screen so they can start immediately. One tap from notification to action. No hunting through tabs.

Everything else -- the scheduling, the timing, the "should I send this?" logic -- lives on the server.

## The Tradeoff I'd Make Again

Server-side notifications are objectively more complex than local ones. Instead of three lines of iOS code, we have a database schema, an API endpoint, a push function, a cron job, timezone conversion logic, and an idempotency layer. That's real complexity.

But the user experience is categorically better. You plank at noon, and your evening reminder never fires. You skip a day, and the reminder arrives right on time. The notification is always relevant, which means the user learns to trust it, which means they actually respond to it.

For a habit-tracking app, that trust is everything. The entire product is built on the premise that a daily nudge keeps the streak alive. If users start ignoring that nudge because it's wrong half the time, we've undermined the core mechanic.

Sometimes the right engineering decision is the more complex one. Not because complexity is good, but because the simpler version doesn't actually solve the problem.
