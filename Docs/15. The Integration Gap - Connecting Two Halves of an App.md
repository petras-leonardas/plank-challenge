# The Integration Gap: Connecting Two Halves of an App

*What happens when you build the frontend and backend separately—and why I'd think twice before doing it again*

---

There's a moment in every project where you step back and realize you've created two complete systems that don't talk to each other. For Plank Challenge, that moment arrived after weeks of focused work on each half.

The iOS app was polished. Every screen worked. The timer counted. Badges displayed. Leaderboards scrolled. Users could browse groups, view profiles, check their streaks. It felt like a finished product.

The backend was production-ready. Sixty-five endpoints. Authentication with Apple, Google, and email. Rate limiting. Error handling. Database indexes optimized. Security hardened. It could handle real users.

But when I looked at the Swift code, I found `MockDataService.shared` sprinkled throughout. Hardcoded users named "Sarah Chen" with 127-day streaks. Fake plank sessions generated with `random()` calls. A fully functional UI powered entirely by make-believe data.

The backend existed. The frontend existed. They just didn't know about each other.

## How Did We Get Here?

This wasn't an accident. It was a choice—though perhaps not a fully conscious one at the time.

When I started building Plank Challenge, I was a designer learning to code. The iOS app came first because that's what I understood. SwiftUI made sense. I could see what I was building. Every change appeared instantly on screen. The feedback loop was immediate and satisfying.

The backend felt abstract by comparison. APIs, databases, authentication flows—these were concepts I knew existed but hadn't internalized. So I deferred them. "I'll figure out the backend later" became the unspoken plan.

To make progress on the frontend, I created `MockDataService`—a simple class that returned fake data for everything. Need a list of plank sessions? Here are thirty randomly generated ones. Need a user profile? Here's a hardcoded "Leo" with made-up stats. Need leaderboard rankings? Here are fifteen fake users, sorted by their fake streaks.

This let me build every screen without waiting for real data. The UI came together quickly. Animations felt right. Edge cases got handled. The design system matured. In isolation, the frontend work was successful.

Then came the backend. Eight phases of implementation, each building on the last. Authentication. Sync. Achievements. Media. Social. Groups. Leaderboards. Polish. Weeks of focused work, documented in blog posts, resulting in a robust API.

But the backend work happened in a vacuum too. I tested endpoints with curl and Postman. I verified database queries worked. I never actually connected them to the iOS app that would use them.

Now here I am, staring at an integration task that feels almost as large as either half alone.

## What the Integration Actually Requires

Looking at the gap honestly, here's what needs to happen:

**Project configuration changes.** The iOS deployment target is somehow set to iOS 26.2—a version that doesn't exist. The app icon folder is empty. There's no entitlements file for Sign in with Apple. No privacy manifest that Apple now requires. These are quick fixes, but they're blockers.

**A complete networking layer.** The app has zero HTTP code. No URLSession calls. No API client. No request building. No response parsing. No error handling for network failures. This entire infrastructure needs to be created from scratch.

**Authentication UI.** The app goes straight to the main screen. There's no login. No signup. No "Sign in with Apple" button. No handling of authentication state. Users can't actually become users.

**Service rewrites.** Every feature currently pulls from `MockDataService`. Every feature needs to instead call the actual backend. PlankService, StreakService, BadgeService, UserService, GroupService, LeaderboardService—each needs to exist, make real HTTP requests, parse real responses, and handle real errors.

**Data model alignment.** The Swift structs don't quite match the API responses. Field names differ. Some fields are missing. The models need updating, or adapters need writing.

Conservative estimate: seven to ten days of work. For context, that's roughly the same as two full phases of backend development.

## How Other Teams Approach This

Talking to friends at startups and reading about how larger teams work, I've learned there are several common approaches to frontend-backend development. Each has tradeoffs.

**API-first development** starts with the contract. Teams define their API—endpoints, request formats, response shapes—before writing any code. Frontend and backend developers work against this shared specification. Mock servers generate fake responses matching the spec. When both sides finish, integration is minimal because they've been building to the same contract all along.

The benefit is smooth integration. The cost is upfront coordination and less flexibility to evolve the design as you learn.

**Backend-first development** builds the API before the frontend exists. The UI then develops against real data from day one. There's no mock layer because there's no need—the real endpoints are available.

The benefit is that frontend developers always work with real data, catching integration issues immediately. The cost is that UI work can't start until backend infrastructure exists, and changing the API means coordinating with frontend developers who are already using it.

**Parallel development with continuous integration** has frontend and backend teams working simultaneously, but integrating constantly. A feature isn't complete until both sides work together. The API evolves through negotiation, with both teams adjusting as they learn.

The benefit is speed—both tracks move forward together. The cost is coordination overhead and the discipline to integrate frequently rather than letting the halves drift apart.

**Frontend-first with mocks** is what I did, whether intentionally or not. Build the UI against fake data, then build the backend, then connect them.

The benefit is focus. Each phase has clear boundaries. Frontend developers don't wait for backend. Backend developers don't wait for frontend. Designers (like me) can see their work immediately without infrastructure complexity.

The cost is integration. The two halves can drift in ways you don't notice until connection time. Field names don't match. Assumptions don't align. The mock data was too simple or too perfect, hiding edge cases the real API exposes.

## What I'd Do Differently

If I started Plank Challenge over, I'd probably take a hybrid approach.

**Define the core API contract early.** Not every endpoint, but the important ones: authentication responses, plank session format, user profiles. Having these shapes locked down would prevent drift.

**Build the networking layer first.** Before any UI work, I'd create the APIClient, the Keychain storage, the request/response handling. This infrastructure exists regardless of which features come later.

**Implement features end-to-end.** Instead of "all frontend, then all backend," I'd build vertically: authentication frontend and backend together, then planks frontend and backend together. Each feature works completely before moving to the next.

**Use mock data strategically, not comprehensively.** Mocks are useful for UI development speed, but I'd limit them to screens I'm actively designing rather than the entire app. And I'd ensure mock data shapes exactly match the API contract.

**Integrate continuously.** Even if features aren't complete, I'd connect what exists to what exists. Early integration surfaces problems when they're cheap to fix.

Would this be slower? In some ways, yes. Context switching between Swift and TypeScript takes mental energy. Building infrastructure before features feels less rewarding. Coordinating with yourself (since I'm the only developer) requires discipline.

But I suspect the total time would be similar—and the final integration phase would disappear. Instead of a concentrated week of connection work at the end, the integration would be distributed across the entire project, each piece small enough to be almost invisible.

## The Work Ahead

For now, I have the integration gap I have. The iOS app and the Cloudflare backend are two complete systems that need to become one.

The path forward is clear, if lengthy:

Fix the project configuration. It's embarrassing that the deployment target is set to a non-existent iOS version, but at least it's a five-minute fix.

Build the networking infrastructure. APIClient, KeychainService, error handling, token management. This is foundational work that every feature will use.

Create the authentication flow. Sign in with Apple button. Email forms. Session management. The RootView that routes users based on auth state.

Connect each feature. Methodically replace MockDataService with real services, one screen at a time. Timer saves to real backend. Streaks fetch from real database. Leaderboards display real rankings.

Polish the edges. Error states that show meaningful messages. Loading indicators that appear at the right moments. Offline handling that degrades gracefully.

I've written a detailed implementation plan—fifteen new files, modifications to a dozen existing ones. It's structured as six phases, each building on the last. The estimate is seven to ten days.

## Lessons for Future Projects

The biggest lesson isn't about process. It's about awareness.

When I built the frontend with mock data, I knew I was deferring work. I just underestimated how much. The mock layer was so effective at hiding the real complexity that I forgot the complexity existed.

Similarly, when I built the backend, I was so focused on making the API robust that I didn't think about the client that would consume it. The endpoints worked perfectly in isolation, tested with command-line tools that don't represent how a real app behaves.

Both halves were successful individually. But success in isolation isn't the same as success together.

The integration gap I face now is a direct consequence of those separate successes. Two well-built systems that need a third project—the integration itself—to become one product.

I don't regret the approach entirely. As a designer learning development, the focused phases helped me build confidence in each domain. Frontend wasn't scary because backend wasn't in the way. Backend wasn't scary because frontend was already working. Each phase had clear boundaries and measurable progress.

But I understand the cost now. And for my next project, I'll pay that cost differently—spread across the timeline rather than concentrated at the end.

## Moving Forward

The integration work starts now. By the time it's complete, Plank Challenge will be a real app that stores real data for real users. The mock users—Sarah Chen with her 127-day streak, Marcus Johnson with his 285-second personal best—will retire to the commit history, their purpose served.

The App Store awaits on the other side of this gap. A week or two of focused work, then a submission, then whatever comes next.

It's fitting, in a way. The whole project has been about building something one day at a time. The integration phase is just another set of days, another set of planks, another streak to maintain.

Let's get to work.
