# Choosing Cloudflare: Why I Bet My Backend on the Edge

**By Leo Bacevicius**

## Introduction

Every app needs a backend eventually. You can prototype with mock data, design beautiful interfaces, and even ship an MVP that works entirely offline—but at some point, users need accounts, data needs to sync, and that "social" feature you promised actually needs other people.

For Plank Challenge, that moment arrived after weeks of building the iOS app. I had a working timer, a streak system, groups, leaderboards—all running on fake data. Now I needed to make it real.

The question wasn't whether to build a backend. It was how.

This is the story of how I chose Cloudflare's developer platform over the more traditional options, and what that decision means for a designer learning to build full-stack applications.

## The Options I Considered

When you need a backend in 2026, you're spoiled for choice. I narrowed it down to three realistic paths:

### Option 1: Backend-as-a-Service (Firebase, Supabase)

The "don't build it yourself" approach. Services like Firebase and Supabase give you authentication, databases, storage, and real-time sync out of the box. You write minimal backend code—mostly configuration and security rules.

**Pros:**
- Fastest time to market
- Authentication handled for you
- Real-time sync built in
- Extensive documentation

**Cons:**
- Less control over data model
- Vendor lock-in concerns
- Can get expensive at scale
- "Magic" can be hard to debug

### Option 2: Traditional Backend (Node.js, Python, Rails)

The "build it properly" approach. Spin up a server, write your API, deploy to AWS/GCP/Heroku. Complete control over everything.

**Pros:**
- Total flexibility
- Huge ecosystem of libraries
- Well-understood patterns
- Easy to hire for

**Cons:**
- More code to write and maintain
- Server management (even with containers)
- Cold starts or always-on costs
- Scaling requires thought

### Option 3: Edge-First (Cloudflare Workers)

The "new way" approach. Serverless functions that run at the edge, close to users. No servers to manage, automatic scaling, pay-per-request.

**Pros:**
- No server management
- Global by default (edge deployment)
- Pay only for what you use
- Integrated ecosystem (D1, R2, KV)

**Cons:**
- Newer, less mature ecosystem
- Some limitations (CPU time, bundle size)
- Learning curve for edge concepts
- Fewer tutorials and Stack Overflow answers

## Why I Chose Cloudflare

I work at Cloudflare. Full disclosure. But that's not why I chose it.

I chose it because when I actually mapped out what I needed, Cloudflare's stack was the best fit for my specific situation:

### Reason 1: I Know the Product

There's immense value in using tools you already understand. I've seen Cloudflare Workers in action. I know what D1 can and can't do. I've read the documentation, attended the internal talks, seen the roadmap.

For a side project where I'm also learning iOS development, reducing the number of new things I need to learn is strategic. I can focus my learning budget on Swift and SwiftUI rather than spreading it across a new backend platform too.

### Reason 2: The Integrated Ecosystem

Cloudflare isn't just Workers—it's a complete platform:

| Service | Purpose in My App |
|---------|-------------------|
| **Workers** | API endpoints, business logic |
| **D1** | SQLite database for users, planks, groups |
| **R2** | Profile images, group photos |
| **KV** | Session tokens, cached leaderboards |
| **Queues** | Background jobs (badges, notifications) |
| **Durable Objects** | Real-time leaderboards (future) |

All of these work together seamlessly. No configuring VPCs, no IAM roles, no cross-service authentication headaches. Everything is in one dashboard, one CLI, one billing account.

For a solo developer, this integration matters more than raw capability.

### Reason 3: Edge-Native is Right for Mobile

Here's an insight that clicked for me: mobile apps are inherently global.

When someone downloads Plank Challenge from the App Store, they could be in Tokyo, São Paulo, Lagos, or London. Traditional server architectures require you to choose a region—or pay for multi-region deployment.

With Workers, I don't choose a region. The code runs in 300+ locations automatically. A user in Sydney hits a data center in Sydney. A user in Berlin hits a data center in Berlin. Sub-50ms latency for everyone, without me thinking about it.

For a fitness app where people check their streak first thing in the morning, that responsiveness matters.

### Reason 4: Cost Structure Matches My Stage

Let's be honest about what stage I'm at: zero users. I'm building something that might never have more than a few hundred people using it.

Cloudflare's free tier is generous:
- 100,000 Worker requests per day
- 5GB D1 storage
- 10GB R2 storage
- 100,000 KV reads per day

That's enough to run Plank Challenge for months—maybe years—without paying anything. No server sitting idle at $5-20/month. No "always-on" database burning money while I sleep.

And if the app takes off? The pricing scales linearly and predictably. No surprise bills because I forgot to set a budget alert.

### Reason 5: I Want to Learn This

Beyond practical reasons, I'm genuinely curious about edge computing. The model of deploying code globally, running stateless functions close to users, managing data with D1's SQLite-in-the-cloud—this feels like the future of backend development.

Building Plank Challenge on this stack gives me hands-on experience with patterns that will matter increasingly in my career.

## The Architecture That Emerged

Once I committed to Cloudflare, the architecture came together naturally:

```
iOS App
    ↓ HTTPS
Cloudflare Workers (API)
    ├── D1 (Database)
    ├── R2 (Media Storage)  
    ├── KV (Sessions, Cache)
    └── Queues (Background Jobs)
```

### The Database: D1

D1 is SQLite at the edge. For my use case—a single-tenant app where each user queries their own data—it's perfect.

I designed nine tables:
- `users` - Accounts and profiles
- `plank_sessions` - The core data: every plank ever logged
- `badges` - Achievements earned
- `groups` - Plank communities
- `group_members` - Who's in which group
- `follows` - Social graph
- `notifications` - In-app notifications
- `devices` - Push notification tokens
- `join_requests` - Group join workflow

The schema uses some deliberate denormalization. User records include `current_streak`, `longest_streak`, and `total_planks` even though these could be computed from `plank_sessions`. The tradeoff: slightly more complex writes for much simpler reads.

When the app loads a profile, it's one query returning one row—not a complex aggregation.

### Media Storage: R2

Profile pictures and group images go to R2. The flow:

1. App requests a presigned upload URL
2. Worker generates URL with 5-minute expiry
3. App uploads directly to R2 (never hits my Worker)
4. App tells Worker "upload complete"
5. Worker queues thumbnail generation
6. Images served via Cloudflare CDN

The "direct to R2" upload is key. User images never pass through my Worker, which has CPU and memory limits. The upload goes straight to storage, then I process asynchronously.

### Session Management: KV

KV stores refresh tokens and session metadata:

```
Key: session:{userId}:{tokenId}
Value: { createdAt, deviceInfo, lastUsed }
TTL: 30 days
```

When a token needs validation, one KV read tells me if it's valid. When a user logs out, one KV delete invalidates the session. "Logout from all devices" is a prefix scan and batch delete.

KV's global replication means session checks are fast everywhere—same data center as the Worker processing the request.

### Background Processing: Queues

Some operations shouldn't block the API response:
- Calculating if a plank unlocks a new badge
- Updating leaderboard rankings
- Sending push notifications
- Generating image thumbnails

These go to Queues. The API responds immediately ("your plank was saved"), and a background Worker processes the queue at its own pace.

If badge calculation fails, the message stays in the queue for retry. The user doesn't see an error, and I don't lose data.

## The API Design

I designed REST endpoints organized by resource:

### Core Resources

```
/auth/*        - Authentication (Apple, Google, Email)
/users/*       - User profiles and discovery
/planks/*      - Plank sessions and sync
/streaks/*     - Streak information
/badges/*      - Achievements
```

### Social Resources

```
/groups/*      - Group management
/leaderboards/* - Rankings
/notifications/* - In-app notifications
```

### Design Principles

**1. Consistent Response Format**

Every response follows the same structure:
```json
{
    "success": true,
    "data": { ... },
    "meta": { "timestamp": "...", "requestId": "..." }
}
```

Errors follow a predictable pattern too:
```json
{
    "success": false,
    "error": { "code": "NOT_FOUND", "message": "..." }
}
```

The iOS app has one response parser, not different handlers for different endpoints.

**2. Idempotent Operations**

Every plank session has a `clientId`—a UUID generated on the device. If the same `clientId` arrives twice (network retry, bug, whatever), the server returns the existing record rather than creating a duplicate.

This makes offline sync reliable. The app can safely retry failed requests without worrying about duplicates.

**3. Minimal Payloads**

API responses include only what the client needs. Profile endpoints don't return plank history. Leaderboard endpoints don't return full user objects—just names, avatars, and scores.

Less data transferred = faster responses = better battery life on mobile.

## Authentication Strategy

I'm supporting three authentication methods:
- Sign in with Apple (required for App Store)
- Sign in with Google (familiar to users)
- Email/password (fallback for everyone else)

All three converge to the same result: a user record in D1 and JWT tokens for the client.

### Token Design

**Access tokens** live for 1 hour. Short-lived, stateless, verified by checking the signature. If stolen, they expire quickly.

**Refresh tokens** live for 30 days. Stored in KV with the ability to revoke. When an access token expires, the app exchanges the refresh token for a new one.

The iOS app stores both in Keychain—Apple's secure storage for sensitive data.

### No Guest Mode

I made a deliberate product decision: no anonymous usage. You must create an account to use the app.

This simplifies everything:
- Every plank belongs to an identified user
- Social features work from day one
- No "conversion" flow later
- No orphaned anonymous data to clean up

The tradeoff is higher friction at first launch. I'm betting that someone who downloads a plank tracking app is motivated enough to create an account.

## What I Learned Planning This

Spending time on architecture before writing code felt unfamiliar. As a designer, I'm used to iterating quickly—sketch, prototype, test, revise. Planning a database schema feels more like drafting blueprints than designing interfaces.

But I've come to appreciate it.

### The Value of Schema Design

Designing the database schema forced me to think through every relationship in my app:
- Can a user belong to multiple groups? (Yes, up to 50)
- Can a group have multiple admins? (Yes)
- What happens when an admin leaves? (Check if last admin)
- Can deleted planks be restored? (No, soft delete for today only)

These questions have to be answered eventually. Answering them upfront, in a document, is cheaper than discovering them mid-implementation.

### Denormalization Decisions

I initially normalized everything—streak counts would be computed from plank history. Then I thought about the query patterns:

"Get user profile" → runs constantly, needs to be fast
"Count all planks by user" → expensive aggregation

So `current_streak` lives on the user record, updated when a plank is logged. More complex writes, simpler reads. The right tradeoff for a read-heavy mobile app.

### API-First Thinking

Designing the API endpoints before implementation clarified what the iOS app actually needs. Some features I'd designed in the UI didn't have obvious API equivalents. Others had API implications I hadn't considered.

For example: "Show recent activity from people you follow" is easy to mockup but expensive to implement. It requires joining follows → users → planks, then sorting and paginating. I moved it to a later phase.

## What's Next

The implementation plan spans eight phases over 8-10 weeks:

1. **Foundation** - Auth and basic user management
2. **Core Planks** - Sync engine and offline support
3. **Achievements** - Badges and progress tracking
4. **Media** - Image uploads and CDN
5. **Social** - Following and discovery
6. **Groups** - Communities and group leaderboards
7. **Leaderboards** - Global rankings and push notifications
8. **Polish** - Error handling, rate limiting, launch prep

I'm not rushing. Each phase has clear deliverables and success criteria. The plan is a living document—it'll change as I learn more.

## Closing Thoughts

Choosing a backend stack is a commitment. You're not just picking technologies; you're deciding what problems you want to have.

With Cloudflare, my problems are:
- Learning edge computing patterns
- Working within CPU/memory limits
- Fewer community resources to lean on

My problems are *not*:
- Managing servers
- Configuring networking
- Multi-region deployment
- Unexpected scaling costs

For a designer building their first production backend, that's the right set of problems to have.

The code is honest. It either works at the edge or it doesn't. There's no "it works on my machine" because there is no machine—just functions deployed globally.

That clarity is valuable when you're learning.
